# CS255
The DriverPass project was designed for a company that wanted to improve the process of scheduling and managing driver training. The client, DriverPass, wanted a web-based system that would allow customers to register for driving courses, schedule driving lessons, take practice tests, and manage their accounts. The system also needed to support employees and administrators by allowing them to manage customers, schedules, training packages, and other business information.
One thing I did particularly well was translating the client’s requirements into system designs that showed how the different users and components would interact. Creating use cases and activity diagrams helped me think through the system from the perspective of the customer, administrator, and other employees. I also did well at identifying the major functions the system needed and connecting those functions to the client’s business goals.
If I could revise one part of my work, I would improve the system diagrams by making some of the relationships and processes even clearer. I would review each diagram with the requirements again and make sure that every major requirement was represented consistently. I would also simplify any areas that were overly complicated so that another developer or stakeholder could understand the design more easily.
I interpreted the user’s needs by focusing on the requirements provided by the client and considering what each type of user would need to accomplish. For example, customers needed an easy way to purchase training, schedule lessons, and access practice tests, while employees needed tools to manage schedules and customer information. I used those needs to determine the system’s functions and user interactions. Considering user needs is important because a system can be technically functional but still fail if it is difficult to use or does not solve the problems users actually have. Designing around the users helps ensure that the final system is useful, efficient, and understandable.
My approach to designing software is to first understand the problem and gather the requirements before deciding how the system should work. I would identify the different users, their goals, and the major system functions. From there, I would use techniques such as use cases, activity diagrams, class diagrams, and other models to visualize the system before implementation. In the future, I would also place more emphasis on reviewing requirements throughout the design process and getting feedback early. This would help identify missing requirements or confusing design decisions before they become more difficult and expensive to fix during development.
Overall, the DriverPass project taught me that good software design is not just about creating a system that works. It is about understanding the client’s goals, translating user needs into clear requirements, and creating a design that developers can realistically use to build a system that meets those needs.
